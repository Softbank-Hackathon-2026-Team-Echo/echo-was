## 1. 목표

보안 통제마다 **언제(준비·실행) 무엇을 어디서 읽어 어떻게 판정하는지**를 표 하나로 정한다.

- 증거 수집(#26), 판정(#27), 매트릭스(#28), 실행 차단(#29), CI 검사(#31)는 이 표를 기준으로 만든다.
- 이전을 사람 승인으로 하든 사전 승인 자동 DR로 하든 **같은 필수 통제**를 통과해야 한다.
- 확인하지 못한 것을 통과로 보이지 않게 한다.
- 이 문서는 최종 발표 요건 "여러 환경의 보안·거버넌스 상태 시각화"와 "이전 전 서버 차단"의 기준이다.

## 2. 확인된 사실 (11/3)

### 2.1 echo-was
- 이전 계획
  - 승인은 개발자 이상 사람만 한다. 기본은 만든 사람 외의 사람이 승인하고, 조직 `allow_self_approval`이 켜져 있으면 자기 승인을 허용한다.
  - 승인 만료(TTL)는 24시간이다.
  - 지문은 승인 때와 일꾼 시작 때 두 번 비교한다.
  - 승인 = 실행 시작이다.
  - 보안 판정을 부르는 곳은 없다.
- 에이전트 토큰(`echo_agt_`)은 GET·HEAD만 허용한다. 쓰기 시도는 403 `AGENT_READ_ONLY`이고 `audit_logs`에 남는다(`app/auth/guards.py`).
- `audit_logs` 결과는 `DENIED`만 있다. 승인·설정 변경 같은 성공한 행동은 기록하지 않는다.
- `ActorType`은 USER·AGENT뿐이다(`app/enums.py`).
- 계획의 `simulated`는 `EXECUTOR_MODE`만 보고 정한다(`app/services/migration_plan_service.py:310`).
  - 운영에서는 진입점 실행기가 http로 켜져 있어 **실제로 트래픽을 옮긴다**(`deploy/base.yaml:136-138`, `http://10.60.0.6:8080` 평문). 그런데 표시는 `simulated = true`다.
  - real 모드에서는 반대로 데이터 확인이 가짜인데 `simulated = false`로 기록된다.
- NetworkPolicy는 Ingress만 있고 egress 제한이 없다(`deploy/base.yaml:50,57,66`). API와 일꾼이 같은 KSA를 쓴다.
- 고객 빌드 워크플로 `.github/workflows/customer-build.yml`
  - 같은 digest를 AR·ECR에 올린다.
  - 보안 검사·출처 증명이 없다(`provenance: false`).
  - 관제탑 이미지 빌드(`deploy.yml`)와 같은 CI 신원·이미지 저장소·빌드 캐시를 쓴다.
- `main` 브랜치 보호가 없다. CODEOWNERS도 없다. main push가 곧 운영 GKE 배포다.

### 2.2 echo-infra · GCP (직접 조회 포함)
- GCP WIF 빌드 신원은 echo-was `main`만 허용한다(`terraform/environments/gcp/dev/ci.tf:29`).
- **방화벽**
  - GCP `internal` 규칙이 내부 대역 TCP·UDP·ICMP를 전부 허용하고 대상 태그가 없다(`network.tf:63-78`).
  - 진입점 80·443이 0.0.0.0/0에 열려 있다(`entrypoint.tf:28-39`).
  - `default` VPC에서 SSH·RDP·ICMP가 0.0.0.0/0에 열려 있다(VM 없음, Terraform 밖 자원).
- **진입점 가중치 API**
  - 평문 HTTP다. 고정 토큰 하나를 `!=`로 비교한다(`entrypoint/weights-api/app.py:391`).
  - 가중치 0인 환경도 fallback으로 트래픽을 받는다.
- **클라우드 간 복제**
  - Postgres 5432를 공개 LB로 노출한다. 허용 IP는 하드코딩이다.
  - `sslmode=require`(자체 서명)다.
  - A쪽 PgBouncer에는 서버 TLS 설정이 없다.
- 실행기 AWS 역할은 EKS ClusterAdmin이다.

## 3. 범위

### 3.1 이번에 정한다 (이 문서)
1. 통제 표: 통제마다 시점·증거 출처·최소 읽기 권한·유효기간·실패 처리·시간 예산(5절)
2. 결과 값과 판정 규칙: 차단·경고·기한부 예외(6절)

4. 검사 도구 선택과 예산(7절)
5. 수동 승인·자동 DR 공통 원칙, AI 결과 취급(8절)

- 이미지 서명, 클라우드 간 mTLS, 별도 GCP 프로젝트 분리

## 6. 판정 규칙

1. **통제 결과:** 증거 하나마다 통제·범위(조직·서비스·환경·digest·설정 커밋)·결과·모드·수집 시각·만료가 있다. 범위가 다르거나 만료된 증거는 쓰지 않는다. 쓸 증거가 없으면 UNKNOWN이다.
2. **필수 통제**(5.1의 "필수 = 예") 중 하나라도 FAIL 또는 UNKNOWN이고 유효한 예외가 없으면 **차단**한다. 사유 코드는 `SECURITY_GATE_BLOCKED` + 통제별 사유(`EVIDENCE_UNKNOWN`·`EVIDENCE_EXPIRED`·`SCOPE_MISMATCH`·`CONTROL_FAILED`·`PRECHECK_MISSING` 등)다.
3. **선택 통제**의 FAIL·UNKNOWN은 WARN으로 보이고 차단하지 않는다.
4. **기한부 예외**
   - 필요한 칸: 통제·범위·사유·승인자(개발자 이상 사람)·만료(최대 7일)
   - 자기 승인 규칙은 이전 계획과 같다. AGENT는 예외를 만들 수 없다.
   - 예외를 만들고 만료되는 것이 모두 감사에 남는다.
5. **AI 결과**
   - `origin = AI`인 결과는 WARN·FAIL·UNKNOWN만 받는다. 저장 직후에는 `confirmation = UNCONFIRMED`이고 판정에서는 WARN으로만 쓴다.
   - 사람이 ESCALATED로 바꾸면 그 결과를 FAIL로 보고, 해당 통제가 필수면 차단한다. DISMISSED는 무시하고 사유를 남긴다.
6. **규칙 우선:** 규칙 결과가 FAIL이면 AI·예외 외의 어떤 값으로도 바꾸지 않는다.
7. **정책 버전:** 규칙표에 버전(`sec-rules-YYYY.MM.DD`)을 붙인다. 판정·사전 승인·이전 계획 지문에 이 버전을 넣어, 정책이 바뀌면 기존 승인을 다시 판정한다.

## 8. 수동 승인·자동 DR 공통 원칙

- 두 모드는 **같은 판정 함수와 같은 규칙표**를 쓴다. 모드에 따라 통제를 빼지 않는다.
- 사전 승인 자동 DR
  - 사전 승인을 만들 때 판정을 하고, 그 정책 버전·증거 ID를 사전 승인에 묶는다.
  - 실행 때는 같은 판정을 유효기간 안의 증거로 다시 한다. 재난이라는 이유로 UNKNOWN을 PASS로 바꾸거나 유효기간을 늘리지 않는다.
- AI는 두 모드 모두 실행 경로에서 부르지 않는다. 사전 점검(C-AI-1)은 준비 단계 결과를 쓴다.
- 판정은 이전 실행 ID와 함께 감사에 남는다(C-AUD-1).

## 10. 사전 부검 (데모 날 기준)
- **P-a 운영 이미지가 C-IMG-1에서 막혀 이전 시연이 멈춘다** → 의존성 갱신을 수요일 안에 담당에게 요청한다. 늦으면 그 차단을 시연 장면으로 쓰고, AI 수정안 → 새 digest 흐름을 보여 준다.
- **P-b Trivy 취약점 DB 갱신 실패로 검사 결과가 없어 UNKNOWN → 전부 차단** → 검사 워크플로가 DB 시각을 결과에 남기고, 유효기간 안의 마지막 결과를 쓴다(cache 모드 표시).
- **P-c 시연 중 인증서·DNS 문제로 C-TLS-1이 UNKNOWN** → 실행 직전 시험은 5초 제한 + 리허설 체크리스트에 주소별 `curl -v`.
- **P-d 게이트를 켠 직후 예상 못 한 차단** → 금요일 종단 시험에서 켜 보고, 토요일 리허설은 켠 상태로만 한다.
- **P-e 사람 점검 기록이 오래돼 근거가 틀림** → 만료 7일, 시연 전날 다시 확인한다.
